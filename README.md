# loggerlib

Библиотека записи сообщений в журнал с уровнями важности и многопоточное консольное
приложение, которое её демонстрирует. C++17, только STL, сборка cmake, целевая ОС —
актуальные Ubuntu/Debian.

---

## 2. Сборка и запуск

cmake 3.16 или новее, компилятор с C++17 (проверяется на gcc 13), pthreads. Сторонних
библиотек нет. Для необязательной цели документации нужен doxygen.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Результат: `build/lib/liblogger.so`, `build/lib/liblogger.a`, `build/bin/logger_app`. Обе
библиотеки собираются всегда из одного списка исходников. `BUILD_SHARED_LIBS` решает только,
с какой из них слинкуется приложение.

### Параметры сборки

| Опция | По умолчанию | Назначение |
|---|---|---|
| `BUILD_SHARED_LIBS` | `OFF` | на какую из двух библиотек указывает `Logger::Logger` |
| `LOGGER_BUILD_APP` | `ON` | собирать демонстрационное приложение |
| `LOGGER_BUILD_COLLECTOR` | `OFF` | собирать коллектор части 3 (ещё не написан) |
| `LOGGER_BUILD_TESTS` | `ON` | собирать тесты и регистрировать их в CTest |
| `LOGGER_BUILD_DOCS` | `OFF` | цель `docs`: документация по публичным заголовкам |
| `LOGGER_ENABLE_WARNINGS` | `ON` | `-Wall -Wextra -Wpedantic` |
| `LOGGER_ENABLE_WERROR` | `OFF` | `-Werror`; в CI включено |

### Документация

```bash
cmake -S . -B build -DLOGGER_BUILD_DOCS=ON
cmake --build build --target docs      # build/docs/html/index.html
```

Недокументированная сущность в публичном заголовке или забытый `@param` роняют эту цель.
В репозиторий сгенерированное не попадает.

### Запуск тестов

`ctest` запускает по одной цели на сьют плюс проверку записи через динамическую библиотеку.
Тестовый бинарник можно вызвать и напрямую:

```bash
./build/bin/logger_tests --list                 # перечислить тесты
./build/bin/logger_tests --suite log_record     # один сьют
./build/bin/app_tests --filter level            # по подстроке имени
```

### Запуск приложения

```
logger_app [--] <logfile> [level]
logger_app [--file <path>] [--socket <host:port> [--proto tcp|udp]] [--level <name>]
logger_app --help
```

`<logfile>` и `--file` — файлы, `--socket` — адреса. Обе опции можно повторять и сочетать:
запись уходит во всё перечисленное. `--proto` задаёт транспорт того `--socket`, за которым стоит
(`tcp` по умолчанию). `--level` (он же второй позиционный аргумент) — начальный порог, одно
из `DEBUG, INFO, WARN, ERROR, FATAL` (регистр не важен, по умолчанию `INFO`). `--` заканчивает
опции, после него имя файла может начинаться с дефиса. IPv6-адрес пишется в скобках:
`--socket [::1]:5555`.

```bash
logger_app app.log --file audit.log --socket 127.0.0.1:5555 --socket [::1]:6666 --proto udp WARN
```

| Ввод | Действие |
|---|---|
| `disk almost full` | сообщение с текущим уровнем |
| `WARN disk almost full` | первое слово — имя уровня, остаток строки — текст |
| `/level DEBUG` | сменить уровень; сообщения, принятые раньше, пишутся со старым |
| `/help` | список команд |
| `/quit` | завершить работу, то же самое делает `Ctrl-D` |
| `//quit` | записать сообщение `/quit` |
| пустая строка | ничего |

Приглашение на ввод `> ` печатается, только когда ввод — терминал.

```console
$ printf 'hello\nWARN disk almost full\nDEBUG hidden\n/level DEBUG\nDEBUG now visible\n' \
    | logger_app demo.log INFO
level: DEBUG
processed 3 message(s), 0 failed

$ cat demo.log
2026-08-19 19:27:45.960Z [INFO] hello
2026-08-19 19:27:45.961Z [WARN] disk almost full
2026-08-19 19:27:45.961Z [DEBUG] now visible
```

`DEBUG hidden` не попало в журнал: порог тогда был `INFO`.

### Коды возврата

| Код | Когда |
|---|---|
| 0 | работа завершена, все принятые сообщения записаны |
| 1 | ошибка в аргументах командной строки |
| 2 | журнал не удалось открыть |
| 3 | хотя бы одна запись не удалась |
| 4 | внутренняя ошибка (исключение, дошедшее до `main`) |

При отказе записи приложение продолжает принимать ввод, печатает причину при каждой её смене
и называет последнюю в итоговой строке:

```console
$ printf 'one\ntwo\n' | logger_app /dev/full DEBUG
log write failed: No space left on device
processed 0 message(s), 2 failed: No space left on device
$ echo $?
3
```

## 3. Библиотека

```cpp
#include <logger/LoggerFactory.hpp>

std::error_code ec;
auto logger = Logger::createLogger(Logger::SFileTarget{"app.log"}, Logger::ELogLevel::Info, ec);
if (!logger) return report(ec);            // файл не открылся

(void)logger->log(Logger::ELogLevel::Warn, "disk almost full");
logger->setLevel(Logger::ELogLevel::Debug);
```

### Цели записи

`createLogger` принимает либо одну цель, либо список:

```cpp
const auto logger = Logger::createLogger(
    {Logger::SFileTarget{"app.log"},
     Logger::SSocketTarget{"127.0.0.1", 5555, Logger::ESocketProtocol::Tcp}},
    Logger::ELogLevel::Info, ec
);
```

Запись при этом **форматируется один раз** и передаётся каждой цели, поэтому штамп
времени совпадает. Правила:

- если хотя бы одну цель не удалось открыть, фабрика сразу записывает ошибку и возвращает `nullptr`.
- если при записи отказала хотя бы одна цель, `log` возвращает `false`, а `ec` называет
  первый отказ. Остальные цели запись всё равно получают.

### Уровни

`Logger::ELogLevel`: `Debug`, `Info`, `Warn`, `Error`, `Fatal` и служебный `Count`. Запись
попадает в журнал, когда её уровень **не ниже** текущего порога. `level2string` и
`string2level` переводят уровень в имя и обратно, `isValidLevel` отвечает, названо ли
значение — в `ELogLevel` можно привести любое целое.

### Формат записи

Одна запись — одна строка; по этому формату пишет `formatRecord` и читает `parseRecord`.

```
2026-08-19 19:27:45.960Z [WARN] disk almost full
└────── 24 символа ────┘ └уров┘ └─ сообщение ──┘
```

- **штамп** — `YYYY-MM-DD hh:mm:ss.mmmZ`, время получения сообщения, **всегда UTC**;
- **уровень** — имя в квадратных скобках, между ним и соседями по одному пробелу;
- **сообщение** — текст с экранированными управляющими символами.

Время, которое не удалось разложить в календарную дату, пишется как
`0000-00-00 00:00:00.000Z`; `parseRecord` эту заглушку отвергает.

### Экранирование

| Символ | В журнале |
|---|---|
| `\` | `\\` |
| перевод строки, возврат каретки, табуляция | `\n`, `\r`, `\t` |
| остальные с кодом ниже `0x20`, а также `0x7F` | `\xNN`, две шестнадцатеричные цифры |
| всё остальное, включая байты выше `0x7F` | как есть, UTF-8 не портится |

Отсюда два следствия: запись не может содержать перевод строки, а `cat app.log` не выполнит
управляющую последовательность из недоверенного сообщения. Преобразование обратимо —
`unescapeMessage(escapeMessage(s)) == s` проверяется по всем 256 значениям байта.

### Границы разбора

`parseRecord` принимает только то, что библиотека способна написать:

- дата должна быть настоящей: `2026-02-31`, `2026-13-01` и `25:99:99` отвергаются;
- не раньше эпохи;
- не позже последнего момента, представимого в `std::chrono::system_clock`. Граница зависит
  от реализации: у libstdc++ тик наносекундный и потолок приходится на 2262 год, у libc++ он
  микросекундный и потолок недостижимо далёк.

### Ошибки

Исключения для бизнес-логики не используются. Три способа, применяемые в библиотеке и
приложении:

| Ситуация | Форма | Где |
|---|---|---|
| ошибка пересекает границу API, на неё можно среагировать | `std::error_code&` | `ILogger::log`, `createLogger` |
| результат либо есть, либо нет | `std::optional` | `string2level`, `parseRecord` |
| несколько исходов, текст адресован человеку | `std::variant`  | `parseUserInput`, `parseOptions` |

`std::error_code` очищается в начале операции и остаётся непустым тогда и только тогда, когда
операция вернула `false` (`nullptr`). Сообщение, отброшенное по уровню, — успех с чистым кодом.

### Потокобезопасность

`log`, `setLevel`, `level` и `isEnabled` можно звать из любого числа потоков: порог хранится
атомарно, запись контролируется мьютексом. Тест пишет 1000 записей из четырёх потоков и
получает 1000 целых строк.

### Две сборки

Символы скрыты (`CXX_VISIBILITY_PRESET hidden`), наружу видно только помеченное
`LOGGER_EXPORT` из сгенерированного `logger/Export.h`. `LoggerBase` через
границу `.so` не наследуется, расширять библиотеку снаружи следует реализацией `ILogger`.

## 4. Приложение

Требование ТЗ — принимать ввод и передавать его в отдельный поток для записи. Потоков ровно
два, связывает их очередь событий:

```
        главный поток                                    рабочий поток
 ┌───────────────────────────┐                    ┌───────────────────────────┐
 │ getline из stdin          │     EventQueue     │ pop, ждёт событие         │
 │ parseUserInput            │  ┌──────────────┐  │                           │
 │   сообщение ──────────────┼─►│ Write        │─►│ ILogger::log ────► журнал │
 │   /level ─────────────────┼─►│ SetLevel     │─►│ ILogger::setLevel         │
 │   /help, /quit, ошибки    │  └──────────────┘  │ счётчики, причина отказа  │
 └───────────────────────────┘                    └───────────────────────────┘
              ▲                                                  │
              └────────── processed(), failed(), lastError() ────┘
```

| Класс | Ответственность |
|---|---|
| `Options` | разбор аргументов командной строки и текст помощи |
| `InputParser` | разбор одной строки ввода: сообщение, команда, ошибка или пустая строка |
| `EventQueue` | потокобезопасная передача событий, ожидание без активного цикла |
| `LogWorker` | единственный писатель: владеет потоком, ведёт счётчики и причину отказа |
| `ConsoleApp` | цикл чтения, диагностика, итоговая строка и код возврата |

### Инвариант завершения

**Ни одно принятое сообщение не теряется.** Держится на трёх вещах:

1. `EventQueue::close()` закрывает очередь для новых событий, но не выбрасывает принятые:
   условие выхода `pop` — пустая очередь, а не факт закрытия;
2. `LogWorker::stop()` закрывает очередь и ждёт завершения потока;
3. деструктор `LogWorker` вызывает `stop()`.

Проверяется тестом: 200 сообщений подряд, немедленный конец ввода, все 200 в журнале.

### Прочие решения

- **Очередь не ограничена.** Предел означал бы выбор между потерей сообщений и блокировкой
  ввода.
- **`processed()` считает записанное, а не принятое.** Поэтому рабочий поток проверяет
  `isEnabled` до записи.
- **Исключения ловятся на двух границах** — в теле рабочего потока и в `main`: исключение,
  покинувшее функцию потока, — `std::terminate`. Пойманное считается неудачной
  записью, текст его ошибки доходит до пользователя.

## Разработка

В CI (GitHub Actions) на каждый push проверяются: сборка и тесты в четырёх сочетаниях
`Debug/Release` × `BUILD_SHARED_LIBS=ON/OFF` с `-Werror`, санитайзеры (thread,
address+undefined), `clang-format`, `clang-tidy` и полнота документации. У тестов свой
`.clang-tidy`, снимающий проверки, которые срабатывают на внутреннем устройстве фреймворка;
в основном коде они остаются строгими.
